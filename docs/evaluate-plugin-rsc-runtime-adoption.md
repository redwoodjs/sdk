# Evaluation: Adopting More plugin-rsc Runtime Behavior in Redwood

## Current Architecture

Redwood currently owns the full runtime layer for RSC (React Server Components).
plugin-rsc (`@vitejs/plugin-rsc`) owns the **build-time / metadata** layer:

- Which modules are `"use client"` / `"use server"`
- Which exports are client references
- Manifest/reference metadata generation
- Build-time transforms for `"use client"` and `"use server"` directives

Redwood owns runtime behavior:

- Route matching (router.ts)
- Worker request handling (worker.tsx)
- `serverAction()` / `serverQuery()` semantics (server.ts)
- `?__rsc` and `?__rsc_action_id` protocol
- GET vs POST enforcement (methodEnforcer.ts)
- Origin checks (methodEnforcer.ts)
- Response wrapping (normalizeActionResult.tsx)
- Redirects/errors/interruptors (router.ts, server.ts)
- CSS/preload injection (worker.tsx)
- RSC stream rendering (renderToRscStream.tsx)

The **bridge code** connects the two worlds via:
- `viteRscManifestAdapter.ts` — converts plugin-rsc `clientReferenceMetaMap` into Redwood's `ClientManifest` format
- `register/worker.ts` — hooks plugin-rsc's `registerServerReference` while preserving Redwood's method/origin metadata
- `register/client.ts` — creates client-side server references using Redwood's `callServer` transport
- `register/ssr.ts` — creates SSR-side server references using `virtual:use-server-lookup.js` generated by plugin-rsc

## plugin-rsc Runtime Behaviors Available for Adoption

plugin-rsc currently provides these runtime capabilities (from source analysis):

### 1. `loadServerAction(id)` — core/rsc.ts
Loads a server action by `file#name` identifier using the RSC environment's module loader.
**Redwood currently does this differently** via `getServerModuleExport` in `ssr.ts`, which uses `virtual:use-server-lookup.js`.

**Adoption feasibility**: LOW — Redwood's approach (`useServerLookup` virtual module) is already based on plugin-rsc's metadata. The difference is that plugin-rsc's `loadServerAction` uses `globalThis.__vite_rsc_server_require__`, while Redwood uses its own `ssrWebpackRequire`. These could be unified if plugin-rsc's require system is extended to support Redwood's module loading.

### 2. `createServerManifest()` — core/rsc.ts
Creates a proxy-based server manifest that maps `id#name` → `{ id, name, chunks, async }`.
**Redwood currently uses its own manifest adapter** (`viteRscManifestAdapter.ts`) for client references and relies on `react-server-dom-webpack` for the server manifest.

**Adoption feasibility**: HIGH — plugin-rsc's `createServerManifest()` can be used directly by Redwood, replacing the custom adapter. It returns a proxy that matches Redwood's expected `ClientManifest` shape.

### 3. `createClientManifest(options)` — core/rsc.ts
Creates a proxy-based client manifest. Supports an `onClientReference` callback.
**Redwood currently uses `createClientManifestFromViteRsc`** which is already a wrapper around plugin-rsc's metadata.

**Adoption feasibility**: HIGH — Redwood's `createClientManifestFromViteRsc` in `viteRscManifestAdapter.ts` could be replaced by plugin-rsc's `createClientManifest()`, which is more lightweight. The `onClientReference` callback allows Redwood to track which client references are accessed.

### 4. `setServerCallback(fn)` / `callServer` — react/browser.ts
plugin-rsc provides a `callServer` function on the browser side that delegates to `globalThis.__viteRscCallServer`, which can be set via `setServerCallback()`.
**Redwood currently sets `globalThis.__rsc_callServer`** directly in `client.tsx` and uses its own `fetchTransport` to make fetch requests.

**Adoption feasibility**: HIGH — Redwood could use plugin-rsc's `setServerCallback()` to register its `fetchTransport`-based callServer, making the client initialization more compatible with plugin-rsc's lifecycle. Redwood would still own the actual fetch logic.

### 5. `createServerReference` — react/browser.ts & react/ssr.ts
plugin-rsc re-exports React's `createServerReference`. On the server-side (SSR), plugin-rsc uses `$$ReactClient.createServerReference` with `$$ReactClient.callServer`.
**Redwood currently wraps `baseCreateServerReference`** from `react-server-dom-webpack` in both `register/client.ts` and `register/ssr.ts`, attaching its own metadata.

**Adoption feasibility**: MEDIUM — Redwood could use plugin-rsc's `createServerReference` exports directly instead of importing from `react-server-dom-webpack`. However, Redwood needs to attach `serverFunctionMetadata` (method/origin info), which plugin-rsc doesn't do. This could be added via a wrapper.

### 6. RPC infrastructure (`createRpcServer`, `createRpcClient`) — utils/rpc.ts
plugin-rsc provides an RPC layer using `turbo-stream` for structured serialization.
**Redwood currently uses `fetch` directly** and `react-server-dom-webpack`'s `encodeReply`/`decodeReply`.

**Adoption feasibility**: LOW — Redwood's RSC protocol is tightly coupled to React's RSC protocol (`encodeReply`/`decodeReply`). The plugin-rsc RPC is designed for dev-server proxy communication, not for production RSC payloads.

### 7. Action encryption (`encryption-runtime.ts`)
plugin-rsc supports encrypting/decrypting action bound args using build-time encryption keys.
**Redwood currently doesn't implement action encryption**, relying on worker-level origin checks instead.

**Adoption feasibility**: HIGH — Redwood could adopt plugin-rsc's encryption runtime for "use server" closure argument binding, improving security. This would need to be wired into Redwood's `createServerFunction` flow.

### 8. CSS/preload injection (`AssetsManifest`, `bootstrapScriptContent`)
plugin-rsc generates an assets manifest at build time with CSS/JS dependencies for client references.
**Redwood currently handles CSS/preload injection in `worker.tsx`** through its own rendering pipeline.

**Adoption feasibility**: MEDIUM — Redwood could consume plugin-rsc's `AssetsManifest` for CSS dependency tracking instead of building its own. However, Redwood's rendering pipeline is tightly integrated with its Document/SSR approach.

## Public API Surface Analysis

Each element of Redwood's public API is evaluated for compatibility if plugin-rsc runtime adoption increases:

| API Element | Current Owner | Could Move to plugin-rsc? | Notes |
|---|---|---|---|
| `serverAction()` | Redwood | **NO** — must stay in Redwood | Core Redwood API. plugin-rsc doesn't have this concept. plugin-rsc wraps functions with `registerServerReference`, but `serverAction()` adds interruptors, metadata, and wrapper support. |
| `serverQuery()` | Redwood | **NO** — must stay in Redwood | Same as `serverAction()`. plugin-rsc treats all server functions the same. |
| Route definitions (`route()`, `index()`, `prefix()`) | Redwood | **NO** — must stay in Redwood | plugin-rsc has no routing concept. |
| Worker-first execution (`defineApp()`, `worker.tsx`) | Redwood | **NO** — must stay in Redwood | plugin-rsc's `serverHandler` is for dev-server middleware only. Production request handling is framework-owned. |
| `?__rsc` protocol | Redwood | **NO** — must stay in Redwood | Determines whether to return RSC payload vs full HTML. plugin-rsc doesn't handle this distinction. |
| `?__rsc_action_id` protocol | Redwood | **PARTIAL** — plugin-rsc could handle dispatch | plugin-rsc's `loadServerAction` could be used for module lookup. But Redwood must still handle GET/POST enforcement, origin checks, and response wrapping. |
| GET/POST enforcement | Redwood | **NO** — must stay in Redwood | plugin-rsc doesn't distinguish GET vs POST for server functions. |
| Method/origin enforcement | Redwood | **NO** — must stay in Redwood | plugin-rsc has no concept of allowed origins or method validation. |
| Redirects/errors/interruptors | Redwood | **NO** — must stay in Redwood | plugin-rsc doesn't support interruptor middleware or redirect handling. |
| Response wrapping (`normalizeActionResult`) | Redwood | **NO** — must stay in Redwood | plugin-rsc doesn't normalize `Response` objects into RSC stream format. |
| CSS/preload injection | Redwood | **PARTIAL** — plugin-rsc's AssetsManifest could be consumed | Build-time dependency tracking could move to plugin-rsc, but runtime injection stays in Redwood. |
| RSC stream rendering | Redwood | **PARTIAL** — plugin-rsc's `renderToReadableStream` could be used | plugin-rsc's `react/rsc.ts` exports `renderToReadableStream`. Redwood wraps it with `renderToRscStream.tsx` for stitching logic. The stitching marker (`#rwsdk-app-end`) is Redwood-specific. |

## Concrete Follow-Up Work Items

### PR 1: Adopt plugin-rsc's `createClientManifest` and `createServerManifest`
- Replace `viteRscManifestAdapter.ts`'s `createClientManifestFromViteRsc` with plugin-rsc's `createClientManifest()`
- Use plugin-rsc's `createServerManifest()` for server manifests
- Remove redundant alias resolution logic (plugin-rsc already handles this)
- **Risk**: Low — backward-compatible if the proxy shape is identical

### PR 2: Use plugin-rsc's `setServerCallback()` for client-side callServer
- In `client.tsx`, replace direct `globalThis.__rsc_callServer = callServer` with `setServerCallback(callServer)` from plugin-rsc's browser runtime
- This aligns with plugin-rsc's expected lifecycle and enables future plugin-rsc features
- **Risk**: Low — purely internal refactor, public API unchanged

### PR 3: Adopt plugin-rsc's encryption runtime for action bound args
- Wire `__vite_rsc_encryption_runtime.encryptActionBoundArgs` / `decryptActionBoundArgs` into `createServerFunction()` in `server.ts`
- This requires plugin-rsc to be configured with `enableActionEncryption: true`
- **Risk**: Medium — encryption keys need to be available at runtime in the worker

### PR 4: Use plugin-rsc's `loadServerAction` for server function dispatch
- In `methodEnforcer.ts`, replace `getServerModuleExport` with plugin-rsc's `loadServerAction(id)` when available
- Fall back to `getServerModuleExport` for compatibility
- **Risk**: Medium — `loadServerAction` uses `globalThis.__vite_rsc_server_require__`, which must be set to Redwood's `ssrWebpackRequire`

### PR 5: Consume plugin-rsc's `AssetsManifest` for CSS dependencies
- In `worker.tsx`, use plugin-rsc's `AssetsManifest` (from `getPluginApi()`) to inject CSS links for client references
- Replace Redwood's manual `scriptsToBeLoaded` tracking
- **Risk**: Medium — requires `getPluginApi()` to be accessible at build time

### PR 6: Evaluate plugin-rsc's `renderToReadableStream` for RSC stream rendering
- In `renderToRscStream.tsx`, use plugin-rsc's `renderToReadableStream` instead of `react-server-dom-webpack`'s
- Keep Redwood's stitching marker (`#rwsdk-app-end`) and `onClientReference` callback
- **Risk**: Low — plugin-rsc's render function is a thin wrapper around the same React API

## Items That MUST Stay in Redwood (Hard Boundary)

These cannot move to plugin-rsc without breaking Redwood's public API:

1. **`serverAction()` / `serverQuery()`** — plugin-rsc has no concept of these
2. **Route matching** — plugin-rsc has no router
3. **Worker request lifecycle** — `defineApp()`, `fetch` handler, middleware chain
4. **Method/origin enforcement** — plugin-rsc doesn't validate HTTP methods or origins
5. **Interruptor middleware** — plugin-rsc has no middleware concept
6. **Response normalization** — `normalizeActionResult`, redirect handling, error serialization
7. **GET vs POST distinction** — plugin-rsc treats all server functions identically
8. **Document/SSR rendering** — Redwood's HTML generation with `renderDocumentHtmlStream`
9. **`?__rsc` vs HTML response routing** — determines whether RSC payload or full page is returned

---

## Conclusion

Redwood **can** adopt more plugin-rsc runtime behavior in several areas (manifest creation, client-side callServer registration, action encryption, asset manifest consumption), but the core public API surface must remain in Redwood's control. The adoption should be incremental, with PR 1 (manifest adapters) and PR 2 (callServer registration) being the safest first steps.

A recommended adoption order:
1. PR 1: Manifest adapters → safe, internal refactor
2. PR 2: Client-side callServer → aligns with plugin-rsc lifecycle
3. PR 6: RSC stream rendering → reduces dependency on react-server-dom-webpack directly
4. PR 3: Action encryption → improves security
5. PR 4: Server function dispatch → deeper integration
6. PR 5: CSS/assets manifest → reduces duplication
